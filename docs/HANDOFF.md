# AIRI 虚拟直播助播：云端交接

更新：2026-10-06。原对话名：规划 Airi 虚拟直播助播。

## 用户目标与确定的选择

基于 AIRI 构建 Live2D AI 虚拟直播助播，在微信视频号和 Bilibili 使用。真人主播是用户本人。希望 AI 能自然搭话、接梗、回复、偶尔插嘴、选择性回应弹幕，参考 Neuro 的可观察互动效果，不需要游戏操作。

用户已经选择：云端开发与云端 AI 服务，直播设备负责麦克风、Live2D 显示和推流。场景为聊天陪伴与知识分享。对话模型使用 DeepSeek。目标仓库：https://github.com/baian-666/ds-zhubo 。

最新需求是把项目对话转到云端，方便在另一台电脑继续。旧对话是本地 Codex 对话，现有 handoff 工具不能将其直接迁到云端。新云端对话属于接续，不代表原始逐条历史或本地文件自动搬迁。

## 当前阶段与用户重点

用户要求先确认大体框架，然后迫切希望早期验证能否形成自然的直播互动。不要在未经试播验证时承诺达到 Neuro 水平，也不要把本地文字原型说成完整产品。应先推进语音试播可行性验证，避免先投入完整平台接入和形象定制。

## 已讨论的架构（设计建议，尚未完整实现）

1. 主播音频进入语音活动检测和流式识别。区分讲话、换气、句中停顿、完整结束。
2. 维护现场状态：主播在对谁说话、当前话题、是否交棒、AI 最近的发言、当前播放位置。
3. 弹幕适配器接入两个平台，统一消息格式，筛选相关、有趣、新鲜、可回答的消息，去重和限流。
4. 独立发言调度器（“直播导演”）决定倾听、表情反馈、附和、接话、回弹幕、短插嘴或主动开话题。
5. DeepSeek 结合人设、本场记忆、近期对话生成短句，流式送入 TTS。
6. AIRI 展示 Live2D、口型、情绪动作，并将实际播放进度反馈给调度器。
7. 云端持久化配置与项目进度，前端浏览器缓存不能代替跨设备同步。

关键修正：不能把“主播一开口就停”当最终规则。“嗯、对”通常是附和；开始新完整句子可能是接管；“等一下、先听我说”或按键属于明确打断。AI 主动插嘴尽量落在微停顿处，短句后让回话轮。正式打断要取消模型、TTS、待播放音频，并丢弃旧话轮迟到结果。

规则处理明确的静音、打断、冷却和过期；语义判断处理模糊的交棒、相关性和参与机会。不要让每条请求串行调用多个大模型造成额外等待。

建议节奏模式：陪聊、讲解、弹幕问答，默认陪聊但主动程度克制。主动插话预算、消息过期和冷却都是试验参数，不是最终体验规则。

## 初期试播验证方案

最小范围：真人麦克风＋识别＋DeepSeek＋TTS＋模拟弹幕，默认 Live2D 形象即可。暂不依赖真实平台评论权限。

先做同模型、同人设、同声音的对照：
- 人工导演：用户手动选择接话时机或弹幕，AI 自己生成内容。用于验证内容、声音与延迟。
- 自动导演：用户自然讲话，由调度器决定发言时机。用于验证节奏判断。

若人工模式也不好聊，先修内容、人设、声音或延迟。若人工模式好、自动差，重点修话轮与调度。人工模式不算自动自然互动验收通过。

覆盖场景：明确提问、讲述途中停顿、用户附和、用户明确打断、未点名的笑点、讲述中大量弹幕、交棒时相关弹幕、话题已经切换。再做十分钟无脚本闲聊，用户不刻意迁就系统。

初期建议验收目标（不是已测结果或 Neuro 指标）：
- 十次明确交棒至少八次顺利接话。
- 每十分钟明显错误打断不超过一次。
- 明确打断后迅速停声，旧回答不再复播。
- 明确交棒后多数接话约一到两秒，频繁超过三秒需排查。
- 有合适机会时，能出现未经点名但用户觉得接得好的主动参与；无机会时允许安静。

录制完整试播并记录识别、决策原因、模型首字、TTS 首音频和播放时刻。目标是连续互动里反复出现有价值的自然参与，不只挑选单段亮点。

## 接续时的操作顺序

按 docs/CLOUD.md 建立或选择关联本仓库的 Codex Cloud 环境，读取当前仓库文件。不要假定新电脑能读取旧电脑路径。

继续与用户确认最小语音试播方案，补齐识别/TTS、模型凭据和可用云环境，再验证真人语音互动。先保留 DeepSeek 作为对话生成选型。

仍缺：云平台及预算、语音供应商、Live2D 模型、每日直播时长、直播设备和平台权限。密钥仅通过 secrets 配置，不要求用户发到对话中。
