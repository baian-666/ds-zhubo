# 边听边理解与短插话

2026-10-19，本机 Fun-ASR 实时识别路径已实现。SenseVoice 整段上传路径仍按原方式工作。最新修改、真实录音和未达成目标见[本轮报告](TURN-LATENCY-2026-10-19.md)。

## 当前行为

- 后端直接接收 Fun-ASR 的增量文本及已确认分句，不再仅把增量用于字幕。最终转写仍是聊天里的正式主播消息。
- 已确认分句或至少500ms保持不变的前缀可以进入提前判断。优先选稳定的标点分句，并把已听到的后续内容一并提供给模型。
- 提前判断与原有参与判断共用任务容量和同一模型。每次调用同时决定等待或准备短句，没有在回复前增加串行规划。提前判断最短间隔1秒，同一分句不因后缀逐字增长反复调用。
- 完整分句的准备结果可跨过少量未完后缀，等待下一个微停顿。超过48字的后缀、转折/否定/纠正信号或前缀改写都会撤掉旧机会。语义仍由模型判断，程序只限定时效。
- VAD在约200ms静音时发送短停顿，约240ms续租一次；700ms收不到新证据就过期。原650ms识别分段阈值不变。
- 提前台词含标点最多4字，使用独立3.5秒冷却，未起声就取消会退还机会。普通主动参与仍15秒。完整问句仍需最终转写与话轮检查，后续流式台词不能把短插话延长成独白。
- 消费准备结果、开始播放前均检查最新文本和停顿。人类恢复讲话时，前端立即取消短插话，后端同时取消对应输出。普通回答的不明讲话约640ms先暂停、仍不明确1800ms再取消，160ms安静重置未暂停前的累计；附和许可可保留，新增非附和内容撤销。模型确认的附和只允许前缀不变、后缀仍是有界附和用语时继承，不能由旧许可保护新问题或接管。真人误停率仍需验证。
- 已播放的短插话在相同最终转写到来时不再触发回答，包括仅标点/空白变化的最终稿。尚未播放就被取消的结果会归还最终回答机会。增加了新内容（尤其新问题）的最终稿仍交给原参与器判断，不因前面的短反应消耗机会。
- 临时转写不写正式主播气泡，不触发叫停快路。实际已播放的短插话会进入送达历史，其输入标记为 `participation=listening`，模型被告知它是当时的临时片段，以最终主播消息为准。
- 关闭收音、换角色、人工停止、静音及新话轮撤销旧机会。短插话不会自行启动或推进主持活动。

短插话在等停顿前已用真实TTS准备PCM，当前从约100ms有效音频即可检查起播；未采用前准备超时8秒、流式缓存最多6MB、候选有效期6.5秒。台词用单条请求，增量裁剪起始静音并保留40ms边缘。角色/模式/声音变化及恢复讲话取消对应缓存。

本地VAD仍保留650ms分段，加入与停顿时钟一致的波形门限，防止模型概率拖尾额外拖延。两条ASR连接减少相邻段冷建连；本地段结束后可以并行准备回答文字，但只有完全一致的最终转写才采用。正式判断时仍未就绪的预备请求会撤销，正常生成立即接续，不能为预生成多等一遍。原先讲话途中完整草稿实验仍关闭。Qwen预热包含尚未提交文字的空任务，保持两条连接；它减少合成启动等待，不能解决ASR尾词迟到。

## 2026-10-19 四秒等待：资料调研后的下一轮顺序

状态：本节保留实施前的源码核对与官方资料方案。首句精简、有限PCM准备交接、有效准备竞速及预热连接保护现已实施，最终同故事3.21/2.62秒，附和/接管实测通过，见[实施与失败记录](FIRST-SENTENCE-LATENCY-2026-10-19.md)。400ms分句未显示收益，已恢复650ms；稳定2秒、持续识别任务及同TTS任务分段提交仍未实现。4.16秒基线见[上一轮报告](TURN-LATENCY-2026-10-19.md)。

### 调研时的基线与边界

- 最后一遍4.16秒约为：识别最终确认1.21秒、确认至回答执行1.72秒、执行至TTS请求0.14秒、首PCM0.75秒、PCM至有声0.34秒。最后一项包含音频自身起始静音和排播，不能全部归因于播放器固定缓冲。
- 已启用的完整回答文字准备从本地VAD段结束开始，最终两遍故事均未复用预备结果；更早的讲话途中完整草稿仍默认关闭。先测有效准备率与取消原因，不能以“功能已开启”代替实际重叠。
- `FunAsrSegment`已设云端 `max_sentence_silence:650`，并非文档默认1300ms；本地650ms与云端识别可能重叠，不得直接相加。`sentence_end`已保留为confirmed，但普通最终输入仍等 `task-finished`。
- 普通模型输出已经流式，动作也已经放在台词之后；仍需读完整的首个decision记录才能交付首句。当前TTS对每个送入的文本块一次性提交后即finish，没有把同一合成任务作为连续文本入口。

### 实施优先级

1. **首句通道先做短、做完整。** 同一次模型流里先确认不可回改的发言权限/对象，再交付一个有实际内容的短分句；说明理由、后续文字与表演信息不得挡住首句。保持单一角色与交付历史，不新增“快速模型先敷衍、主模型再回答”的串行调用。要保留严格解析与字段校验，不能把未闭合JSON直接当可播放文本。记录首token、首个可交付分句、原始/缓存命中token数，区分模型首token慢与结构化输出过长。
2. **让有效首句提前准备，并交接同一份音频。** 在稳定、已经成义的输入上尝试一个短首句，和识别收尾并行；先统一后端预备与前端分句/PCM所有权，避免此前整段预合成与前端切分不一致而重复请求。最终文本/问题变化、恢复讲话、换角色、叫停均废弃旧准备；无可用准备按原时点正常回答。保留单个有效候选及重试上限，不直接重新开启旧完整草稿实验。
3. **验证分句确认能否早于任务结束可靠使用。** 区分云端确认的句子、传输任务结束与人类交棒。只有音频序号/时间戳证明确认已覆盖该输入，才允许较早衔接；尾字、后续否定与纠正必须能撤销未播放结果。先测两者实际差距；持续识别任务与降低断句阈值属于候选实验，不承诺仅改650ms就能节省一秒。
4. **再决定是否更换慢环节。** 若识别尾延迟仍占主导，先对同服务其他实时ASR作中文原音频对照；若模型首token仍慢，比较稳定提示前缀/精简输入后再考虑更快模型。TTS尝试同任务分段提交前先对一段原声做音质检查，通过后才重复计时。不以模型宣传首包延迟代替本机全链路数据。

实施按第1项再叠加第2项推进，已同时记录第3项的时间差：本次最后确认句与任务完成多数同时到，不能声称提前采用确认句就能明显提速。后续扩大ASR生命周期改造仍需证据。每个候选继续用原故事、长附和和接管音频；分别统计首个有内容的声音、完整交付、误抢/误停、接管停声、取消后复播、断流和废弃计算量，不把“嗯/好的”当正式回答变快。

阶段目标是把普通闲聊的首个有内容回应推向约1.5–2秒，并在多次配对样本里同时检查尾延迟；这是待验证目标，不是预测保证。附和不停、接管及时停和原音色保持是采用条件。真人和外放回声仍需独立验收。

## 2026-10-18 真人少插话与长等待：下一轮计划

以下为2026-10-18原计划，保留当时判断及验收要求；2026-10-19实际实现与失败/通过证据见[本轮报告](TURN-LATENCY-2026-10-19.md)。用户反馈是实际聊天几乎没有中途接话，停声后通常等5～6秒；这应作为当前体验问题，不能用旧版本偶尔插话成功或单次4.59秒否定。下面为原执行顺序，2026-10-17计划中的取消、所有权、附和/接管验收约束继续有效。

### 判断与尚未证实的原因

- 现有Fun-ASR路径能收增量文本，但中途发声仍是一条严格受限的短反应路径：稳定前缀500ms、判断最短间隔1.8秒、同一参与任务通道、含标点最多4字、15秒主动参与冷却、完整短句TTS就绪、当前停顿许可同时成立。候选还可能因修订、后缀变化或6.5秒有效期失效。这些是源码事实；哪个条件漏掉了真人机会，尚无逐机会统计，不能直接认定某一项是主因。这些等待可能重叠，不能简单相加当实测。
- 完整回答仍依赖最终转写。旧版同音频4.59秒中，波形结束至提交finish约1.48秒，提交至最终识别约0.49秒；前者含本机端点/队列等待和时间轴映射误差，不能全部归因于云端识别。原始证据见[提前准备报告](ANSWER-PREPARATION-2026-10-18.md)。
- 当前统一导演、手册、MCP及声音无指令版已有其他对话的修改；旧计时不是当前基线。短反应/接管判断目前已经排除MCP查询，普通闲聊也没有强制查询前置步骤，不能未经测量就归咎于MCP。
- 必须确认实际运行的桌面产物、后端与ASR路径。SenseVoice仍整段上传；不能把Fun-ASR源码存在视为用户会话已经走流式路径。

### A：一次基线把漏接话和等待拆清楚

- 核对实际运行版本和生效配置，仅记录非敏感标识。音频试验入口默认会启用完整回答提前准备，而生产默认关闭；对照必须显式对齐开关，并核对是否使用当前统一导演、手册与声音路径，结果内保存实际配置，不能拿不同流程互比。
- 对原连续故事逐个标注适合接话/应该继续听的位置。为每个机会记录：稳定文本何时可用、是否提交判断、模型选择等待还是回应、冷却/忙碌/长度限制、候选是否过期或因何撤销、TTS何时可播、停顿许可何时出现、最终是否完整出声。输出漏接话原因及分母，不能只看“listening已启用”。
- 同一音频时钟标记输入最后声波、200ms停顿、VAD结束、上传队列清空、finish发送、最终转写、模型首个有效台词、首PCM、排播及首个可听内容。跨进程事件经校准并标记误差；冷/热启动、查资料与普通闲聊分开。
- 先完成一个当前默认版真实音频样本及试听，再选占比最大的等待点改动；这一阶段不扩成历史日志审计，也不等待全部长期验收才开始修复。

### B：优先让准备好的短反应赶上自然停顿

- 将听者短反应与主动展开话题的冷却分开。短反应按新语义、距上次实际发声时间、重复程度决定是否值得准备；不沿用完整发言的统一15秒禁入，也不按每分钟次数强制插话。未播就撤销的候选不消耗下一次机会。
- 你还在讲时完成语义选择和声音准备；停顿到来只检查新证据并发声，不再从头做模型判断和合成。短反应使用有界相关上下文，保留角色及适用偏好，不附带无关的主持/表演长历史；不在正常回答前增加第二次串行模型调用。
- 检查是否可在首段PCM达到可连续播放的缓冲量后起播，而无需等整条短句合成结束；用真实听感验证断音风险。另作小规模候选：少量同一克隆音色的预制短反应，仍由语义选择且限制重复，先试听后决定是否采用，不能随机播放“嗯嗯”充数。声音保持无instruction版。
- 候选绑定所回应的分句及输入修订。无关后缀增长不必全部重做；否定、纠正、先听完、明确停止及失去话轮必须撤销。先保留现有短反应长度验证命中和让话，再单独试一个自然短分句；不能只放大4字上限。
- 先保证准备好的声音能在自然短停顿起播、你恢复说话能及时停。持续讲话期间的重叠附和属于后续独立实验，必须先验证回声和听感，不通过取消让话保护获得“插话率”。
- 首次可感知交付：在原故事中预先标出的适合窗口听到贴切、完整的回应，同时恢复讲话样本不退步；报告漏掉和误抢的窗口，不能只挑一次成功。

### C：同步消除最终转写前的本机等待

- 依A的时间线处理VAD回调、推理积压、串行上传和结束请求顺序。优先消除额外排队/重复等待，保留所有应上传音频；不要直接把650ms端点降到200ms，造成句中换气截断或错误交棒。
- 分开“识别传输段结束”“一个语义分句稳定”“用户让出话轮”。同一逻辑表达可跨多个识别段累计，最终确认按音频顺序合并，不把临时改写写入正式历史。
- 对比现有每段任务与持续ASR任务的分句结果利用方式，只在测到建连/finish确有明显成本时扩大改造；断线重连、乱序、尾音与纠正必须有回归。持续识别本身不等于可以随时抢话。
- B与C分别可回退，但首批效果一起验收：既减少漏掉的中途机会，也减少用户交棒后的空白。

### D：有边界地提前准备首句，再改善完整回答

- 已撤回的完整草稿实验继续默认关闭。先取得长流失败的明确错误类别并修复，同时补上ASR把附和误转成新内容的反例；不把此前失败都归因于提前生成，也不把某次快样本当重启依据。
- 改为稳定语义足够时仅提前准备一个有实际内容的首句，后文仍用最新上下文展开；明确新问题、否定或纠正使准备失效。绑定同一话轮/输入版本，保留单一播放所有权、有界并发及废弃成本记录。
- 最终交棒时复用有效结果；没有可用结果立即走正常流式生成，不能先耗尽准备超时再额外等待一次完整请求。被取消的模型/TTS/缓存不能在后台排到新回答之前，也不能复播。
- 首声统计必须是贴切且有内容的回答；“嗯，我想想”不能作为完整回答提速成绩。若分段实测仍说明供应商首字/首PCM是主要下限，再小范围比较可替代模型或服务，保持现有角色和声音作为对照，不先迁移整套框架。

### 验收与发布门槛

- 每个候选先试听原连续故事的一次真实回放，经过实际VAD、Fun-ASR、DeepSeek、Qwen及WebAudio；听感合格后做小批交替顺序配对，失败和超时不删除。进入发布评估后沿用下文至少30次有效配对、40例附和及15分钟真人试聊的目标；样本不足只报告初步结果。
- 完整回答首声目标仍是P50约2秒内、P95约3秒内，属于待验证目标，不承诺现有服务必然达到。阶段目标是同音频配对有稳定改善，分别报告各环节而非只给最快数。
- 短反应让话P95不超过300ms、普通接管P95不超过800ms仍是待验收目标；已有约0.7～0.8秒单次结果不等于分位数达标。附和误停、播放断裂、旧语音复活均不能被更快首声抵消。
- 中途接话统计人工标注窗口中的有效完整回应率、禁止窗口误抢率、内容贴切度及重复率；第一轮据基线确定提升幅度，不设强制插话频率。
- 原故事、长附和、接管、恢复讲话为固定回归，再覆盖更正/否定、句中换气、明确叫停、无停顿长讲。软件回放与真人/物理外放录音分列；只有软件音频通过时不能宣布真人体验问题解决。
- 实现批次执行项目必需检查；改AIRI须保留可重放源码并完成相应检查和构建。隔离会话先验收，再备份发布匹配前后端；当前规划本身不修改运行服务。

参考：[LiveKit官方话轮调优](https://docs.livekit.io/agents/logic/turns/tuning/)将端点判断、打断与提前生成分开处理，支持有界提前准备的设计方向，不代表要引入LiveKit；[阿里Fun-ASR客户端事件](https://www.alibabacloud.com/help/en/model-studio/fun-asr-client-events)区分分句静音参数与任务结束。具体收益必须由本项目当前版本音频验证。

## 2026-10-17 自然聊天改进计划

状态：第1、2批首项“附和与接管协调”已进入实际音频验证，结果和未完成范围见[修复记录](FLOOR-AUDIO-FIX-2026-10-17.md)。以下仍是完整设计与验收目标，不代表所有阶段已完成。本计划基于当天全链路代码审查，兼容最新的自主主持、closing、yieldToHost 和 Qwen 两路提前合成。部署事实以 [STATUS](STATUS.md) 为准。

目标顺序：附和不误停、接管及时停 → 在合适时机完整接一句 → 连续理解和正确续接 → 降低首声等待 → 改善长聊一致性。保留当前 AIRI、Fun-ASR、DeepSeek、Qwen 克隆音色及播放所有权；每批独立验证和回退。

### 第0批：建立当前版本的音频基线

- 固定后端源码指纹、桌面构建、角色、模型、声音、配置及会话快照。当前代码与旧录音并非同一组合，旧结果只作参考。
- 复用原连续故事和恢复讲话音频，补充长/短附和、直接叫停、引用叫停后要求继续、句中换气、转折纠正、长于30秒无明显停顿、笑声、背景人声、外放回声场景。为可插话区间和禁止抢话区间做人工标注，记录争议，不以“插得越多越好”评分。
- 补全关联输入段、逻辑话轮、决定、文本句段、TTS请求和实际播放的编号。录音的双声道共同时间轴用于起音/停声测量；跨进程时钟只作有标识的诊断，不直接相减冒充声学时延。
- 产出：完整基线录音、阶段耗时、失败清单和配置清单。先每候选试听一个样本，听感合格后再重复计时。此批完成后再确定最值得优化的等待阶段。

### 第1批：让所有控制看到同一份话轮与播放状态

- 在现有 Director/Scheduler/Participation/Hosting 之间增加小型话轮协调模块。统一维护谁持有话轮、输入是否仍未完、正在播放的句段、待播放句段、取消原因及修订号。模型给语义建议，协调模块按权限和最新状态落实动作。
- 麦克风事件、文字输入、叫停快路、模型决定和主持安排都通过这份状态核对；每个决定绑定输入修订和目标输出，过期建议不能改变新话轮。前端保留无需等待网络的减音/停声能力，但其事件必须回传并收敛到后端状态；前端不能自行恢复已取消语音。
- 给导演提供有界的临时播放上下文：已确认送达的句段、当前句及播放进度、已生成未播放的后文。未播内容明确标记为计划，不写成已经说过的话。
- 音频进度先记句段ID、音频时间及“不确定的部分已播区间”。现有TTS没有可靠字词对齐时，不按字符比例伪造精确已听文本；长期记忆仍只接收确认送达内容。
- 保留 closing 对整轮播完后的安排；新的接管、取消或输入修订使旧 closing 失效。观众不能撤销人工停止，短反应不自动推进主持。
- 主要落点：`apps/cohost/director.mjs`、`participation.mjs`、`scheduler.mjs`、`hosting.mjs`、共享契约和 `integrations/airi/use-cohost-voice.ts`。
- 退出条件：新状态先在不改变发声的影子模式中核对；旧结果不复播、角色/窗口切换不串话、普通附和不重开回答，且新增上下文不会显著拖慢首句。

### 第2批：统一附和、接管和明确停止的处理

- 明确区分继续当前回答、让出话轮、取消当前回答和保留短暂待判断状态。保留明确叫停的快速取消，不让这条路径等待另一次云端规划。
- 她说话时也允许新ASR证据进入有限的语义判断，结合当前句和后文识别“对，你继续”“我有个新问题”“先听我讲完”；使用现有模型任务通道，不在普通回答首句前串联第二次模型调用。
- 声学证据仍提供快速保护，但不再把固定时长本身等同于语义接管。语义迟到时，有界地优先让人说；模型失败/超时不能造成无限重叠讲话。
- 试验可恢复的短暂减音或暂停：只有确认是附和、用户已结束这次附和、输出和话轮修订仍相同且未收到停止时，才允许从保留位置继续。暂停期间冻结后文播放，限制预生成音频，口型/动作时钟同步暂停。超时或确认接管则彻底取消模型、合成、排队和缓存；明确停止绝不自动续播。
- 可恢复机制先独立开关验证；若频繁闪断、重复字或接缝难听，保留已有取消方式，重新调整判据。误暂停造成的卡顿也计为体验失败，不能只统计彻底取消率。
- 主要落点：话轮协调模块、`speech-pause.ts`、`use-cohost-voice.ts`、`speech-pipeline.ts`、播放/表演时钟。
- 退出条件：同音频下长附和误停下降，真实接管停声不退步，引用/否定叫停不误判；停止后迟到音频和弹幕均不能让旧回复复活。

### 第3批：把音频分段与一句话是否讲完分开

- 为同一连续表达建立逻辑输入ID；650ms停顿或VAD容量切段仅结束识别传输段，不直接等于交棒。按语音发生顺序累计确认片段，后段开始不清空已理解的前文；迟到结果按输入版本合并。
- 分开保存稳定内容、可变尾部、尚未讲完的问题及明确纠正关系。修订影响相关候选和未播内容，不每次逐字增长都重跑整轮；识别段失败须标记缺口，不把缺失内容补成事实。
- 让准备回答与发声许可分离：边听时可提前准备，实际发声仍需合适的内容与当前话轮证据。用户继续讲话、纠正前意或要求先听完时撤回不合时宜的候选。
- 先保留当前短反应长度完成上述重构；稳定后再试验一个自然短分句，以当前音色真实音频时长和内容完整性评估长度。不能只把4字上限放大，也不能把每个停顿变成追问。
- 普通完整回答可利用仍有效的已理解前缀或准备结果；只有确认交棒后才持续展开。后续生成若依据已被推翻，取消未播部分并重新准备，已说出的内容需要自然纠正，不悄悄改历史。
- 主要落点：`recognition-turns.ts`、`streaming-recognition.ts`、`live-listening.mjs`、`participation.mjs`、流式回答和候选版本校验。
- 退出条件：30秒以上连续故事跨识别段不丢上下文；出现适合接话的地方能完整接一句；末尾新增问题仍能回答，转折后不播旧候选，已经说过的短反应不重复。

### 第4批：针对测出的瓶颈降延迟，并补场次一致性

- 依据第0～3批时间线分别优化识别尾延迟、模型首句、合成供给和状态到播放的等待；保留流式首句及云端有界提前合成。控制提示上下文和后台判断频率，用取消/废弃率、调用量与音频时长检查预生成成本。
- 不固定新增规划调用，也不为了数字快而先说空洞填充词。预合成只有在听感合格、实际节省等待且废弃成本可控时扩大。
- 在现有SQLite场次记忆中逐步加入有来源的事实/说法、人物归属、更正关系、公开待续事项及角色虚构设定标记。用户/观众说法和模型推断分别保存；模型生成的故事不能因进入历史就升级为现实亲历。来源标签用于约束归属，不宣称它能自动核验事实真假。
- 退出条件：回复等待有配对改善且无抢话回归；长聊中能保留刚才的更正，不把观众经历归给主播，不把未播放内容当成共同记忆。真实性仍以完整试演记录评估。

### 验收口径和初始目标

以下数字是待基线校准的工程目标，不是成绩或性能保证。安全/所有权回归必须通过；自然度和延迟必须同时报告，不能以更多误抢话换取更低延迟。

| 项目 | 口径与第一轮目标 |
| --- | --- |
| 短反应让话 | 从录音中人类恢复讲话到AI最后可听音，目标P95不超过300ms |
| 普通回答接管 | 从人类开始实际接管到AI最后可听音，目标P95不超过800ms；确认叫停后的决策耗时另报 |
| 附和误停 | 长短附和分别统计，合计至少40例；取消或明显停顿/重新起句合计不超过5%，同时报告分母 |
| 完整回答首声 | 从人类真正交棒到AI有内容的首声；优化目标P50约2秒内、P95约3秒内，若当前供应商达不到则报告分段瓶颈 |
| 改造额外等待 | 同链路配对，沿用架构路线目标：P95增量同时不超过150ms和基线10% |
| 中途接话 | 报告人工标注合适窗口中的完整有效接话率、禁止窗口误抢率与内容是否贴切；不设每分钟必须说几次 |
| 旧语音复活 | 全部取消/角色切换/失租/停止场景中为0；出现一次即阻止该批发布 |
| 长聊听感 | 至少一次15分钟真人连续对话，耳机和外放分别验收；保留整段录音，标记抢话、误停、重复、长空白和内容失实 |

音频回放须经过实际VAD、Fun-ASR、DeepSeek、Qwen和播放链路，不允许用注入文字或模拟事件替代。每个候选先听一个样本；合格后再做至少30次有效的配对延迟测量，冷/热启动、失败和超时分别报告，不删除失败重试。WebAudio双声道录音证明软件音频时序，外放与真人需实际麦克风/录音验证；没有物理录音时明确保留这一缺口。

### 落地与回退

- 开发顺序为0→1→2→3→4；第1、2批组成第一项用户可感知交付，先验收“附和不停、接管能停”，再放宽插话能力。暂不承诺日历工期，以每批真实音频的结果决定下一批。
- 每批重读最新STATUS并核对相关源码，兼容其他对话期间的新修改；保留现有未提交改动、角色、声音和聊天。控制开关仅用于开发对照和回退，不增加日常设置负担。
- 改原型执行 `npm run check`、`npm test`；改AIRI先读其指南，完成相关类型/测试及固定桌面构建，覆盖源保存在 integrations/scripts。确定性测试重点是取消、过期、合并修订和所有权，不代替音频验收。
- 候选版先在隔离会话完成真实音频与试听；验收失败保留证据并修复。通过后备份会话，按匹配前后端版本发布，出现回归回退该批；不覆盖原运行数据库。
- 若现有声音信息和推理速度使第2、3批目标持续无法兼顾，再针对明确缺口评估韵律/话轮模型或音频理解适配层；届时才比较具体方案及当前接口，不先以更换整个语音框架作为前提。
