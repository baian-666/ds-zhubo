# 场次持续性：恢复、摘要与待续事项

更新：2026-10-15。用户决定暂缓延迟优化，继续架构路线的批次 4。

## 使用方式

日常入口仍是 `启动小鲸鱼.cmd`。后端自动保存本场，重新启动时恢复记录和有限上下文。
AIRI「设置 → 直播助播 → 本场记录与记忆」显示保存状态及当前角色带入的对话轮数。
“清空本场，重新开始”需在界面确认一次，会停止当前回答，清空本场全部角色的短期记录。
角色卡、声音设置、原生 AIRI 聊天和手动备份保留。原生 AIRI 聊天与直播记录仍是两个入口。

展开“场次摘要与待续事项”可查看原话摘录、来源时间、待续状态，或移除某一项。
可以试说：“我先打一局，稍后再聊猫把跑步机当床的事，先记着。”之后说：“打完了，接着聊刚才猫的事吧。”

## 保存范围

数据库为本机忽略文件 `data/cohost-session.sqlite`。使用 Node 内置 SQLite，无新增服务或模型调用。

| 信息 | 当前范围与语义 |
| --- | --- |
| 聊天气泡 | 最近 300 条，包括完整生成文本、公开导演理由、试听与播放状态 |
| 现场观察 | 最近 60 条，另有约 12,000 字符预算；保留主播/观众来源、时间及话题 |
| 模型对话历史 | 每个角色卡、每个回复引擎最近 6 轮已交付对话；所有角色合计最多 96 轮 |
| 声音交付 | 保存已确认的文本前缀；中断后未确认部分不进入模型历史 |
| 摘要来源 | 最近 96 条短原话，每条最多 240 字符；观众最多 24 条，避免弹幕突发挤掉主播对话 |
| 场次摘要 | 按话题和每 3 条主播话分段，均匀选最多 4 段的主播/助播摘录；每角色最多 8 条，全局最多 48 条 |
| 待续事项 | 每角色最多 4 项待续、默认 2 小时有效，全局最多 24 条含已接续/取消/过期记录 |
| 配置与大文件 | TTS 普通配置存同库的独立表，角色卡仍归 AIRI，服务凭据仍在 `.env`；数据库不保存凭据或音频 |

这是有限场次记忆，不是全场无限历史或长期人格记忆。摘要采用原话抽取，没有新增向量检索、每轮反思或后台模型循环。
角色卡 ID 区分助播历史；同一场主播和观众观察共享。另一角色说过的台词不会冒充当前角色的回复。
修改同一卡的人设不自动删除历史；切换角色时取消旧角色正在生成的回复及待执行决定。

## 恢复与交付边界

- 显示的完整生成文本不等于已说完。模型仅收到文字路径已完成回复，或音频路径已确认前缀。
- 进度回执更新同一交付 ID，不重复新增历史。正常结束保存完整记录，中断保留确认部分。
- 重启把未完成气泡标为中断，现场中的 `partial` 交付标为 `interrupted`。提示词说明后文是否听到未知。
- 回执仍是现有播放器的文本进度，不是实体扬声器检测或音素对齐。断电与回执之间存在未知区间。
- 恢复后的旧现场进入旧话题。导演、观众待回复队列、45 秒临时便签、麦克风与播放租约不恢复。
- 话轮音频 ID 带运行时代次。旧客户端即使碰巧提交相同数字话轮，也不能确认新一轮播放。
- 手工 `--room-snapshot` 只用于空数据库首次导入显示记录，不能据旧气泡补写模型记忆。
- 已有数据库时拒绝再导入手工气泡快照，避免旧备份覆盖新记忆。

首次部署保留旧气泡，新对话开始累计可恢复的模型历史。未伪造先前对话的播放结果。

## 摘要与待续边界

摘要在现场空闲时整理，不等待它才能接话，也不调用另一轮模型。保留角色、时间、话题、原话和部分交付状态，观众说法不会变成主播事实。摘要可以截短，不能代表整个场次的完整经过。模型每轮最多读取 8 条、每条 160 字符的摘要，以及 4 项待续；这增加少量输入上下文，不声称绝对零耗时。

自动参与模型沿用同一轮调用。`continuation.defer` 必须逐字引用本轮主播明确的“稍后/先记着”请求，不能由弹幕或普通等待建立。主题标题必须来自原话，否则回退到原话。流式回复先送首句，待续维护字段放在末尾的可选 presentation；错误字段被丢弃，不阻断正常台词。

- 持久待续没有独立发言计时器，不触发静默轮询模型。只在新的主播/观众机会中作为上下文，只有新的主播话能维护事项。
- 换话题/重启后标为旧话题，只有主播明确“继续/回到刚才”时允许接续；仍受原有静音、主持权和冷却约束。
- `resume` 必须引用本轮提供的事项 ID，且只能用于回复主播。只有本轮完整文字/音频确认交付后标“已接续”。只播一部分则仍待续，重启不会重播。
- “已接续”说明相关回答已交付，不是外部任务完成证明。没有新增上网、调工具或自动执行外部任务。
- 明确取消、过期和手工移除都会使该事项退出后续上下文。移除/清空后的迟到维护指令被代次校验拒绝，不能把已删事项复活。
- 原有 45 秒临时想法仍独立存在；有效持久待续不会同时建立该临时想法，避免另开一次静默复查。
- 人工直接回复和明确称呼的旧快速交棒路径也能读取摘要/待续，但暂不自动写维护字段。没有为标记状态额外调用模型；必要时在设置中移除已聊过的事项。

“清除当前摘要”删除当前角色的摘录和摘要来源，不删除近期现场、已交付历史及其他角色。要让本场所有上下文失效，使用“清空本场，重新开始”。清空操作仍保留手工独立备份。初次升级不根据旧显示气泡补造摘要，从新现场与已确认交付开始积累。

## 写入、失败与备份

`SessionStore` 是存储边界，当前用单个事务保存有上限的场次检查点。
它还不是完整事件溯源系统。生成过程最多每 200ms 合并写入，输入、交付回执和完成边界及时提交。
使用 WAL 与 FULL 同步。数据库保存显示、观察和模型历史的同一版本，避免只恢复一半。
进程租约阻止第二个后端抢写。异常退出后仅在原进程已不存在时接管，版本检查防止外部修改被覆盖。
PID 被系统复用时保守拒绝启动，需要人工核对占用进程；不会擅自终止进程。

写入失败在原生设置中提示，当前对话继续，最后有效检查点保留。损坏或未知版本数据库拒绝加载，不自动清空。
清空本场同时清空现场与模型历史，并检查点截断 WAL。用户手动保存的独立备份不随此按钮删除。

在项目根运行以下命令，可对运行中的数据库生成一致备份，不需停 Index 或桌面：

```powershell
./data/toolchains/node-v26.7.0-win-x64/node.exe scripts/backup-session.mjs
```

备份位于 `data/session-backups/`。恢复需停止 cohost，保留现数据库与 WAL/SHM 文件后再替换，不能直接覆盖运行中的库。
备份不携带旧运行时租约。自动化测试覆盖备份可重新打开、来源不变和禁止覆盖现有备份。
临时回退可用后端参数 `--no-session-store`，回到内存模式；原数据库保留，回退期间的新内容不会写入它。

场次批检查点 JSON 从 format 1 升为 2，当时 SQL 版本为 1。后续普通配置批将 SQL 升为 2，检查点 JSON 仍为 format 2，详见 [普通配置仓库](RUNTIME-SETTINGS.md)。不支持新版本的旧后端会拒绝打开，不能直接与新数据库混用；后端回退需停服务、保留新库，再使用匹配的升级前备份。桌面构建回退不降级后端数据库。
