# 留白后的时间感知与主动复查

本页保留此前方案及部署证据。用户随后要求不设定点唤醒，持续模式已改为[持续观察、自主选择](DIRECTOR-OBSERVATION-2026-10-20.md)。下文30秒和预约秒数不再描述当前持续模式。

2026-10-20。用户反馈：小鲸鱼认为只有主播开口时才会收到时间，因此留白后不知道什么时候再开口。

## 发现与修复

运行时已有100ms调度检查、预约复查和持续主持30秒静默观察。问题不只是缺少一个查时间工具：模型指令仍同时含有“0总是不再唤醒”“没有新主播话只能考虑弹幕”等旧规则，和持续主持相互冲突。原有`withoutInputMs`包含自己的讲话，`audienceWaitMs`仅适用于观众交棒，缺少通用留白耗时、唤醒原因和上次等待决定。

- 正常参与和定时复查主动携带`clock`：当前毫秒时间、UTC ISO时间、Asia/Shanghai当地时间。时间进入既有导演请求，普通聊天不额外调用模型或MCP。
- 主持上下文增加`pauseElapsedMs`（本次留白经过时间）、`quietMs`（连续无播放/无输入的安静时间）、`sincePlaybackMs`（最近一次真实交付后的时间）。重复选择等待不会把已经持续的安静错误归零；新的留白计划有独立起点。
- `wakeup`保留外壳为何、何时发起当前观察：预约、静默、重试、开始、恢复或输入。原定截止时间在触发后仍提供，不会因清空`nextReviewAt`而丢失。`previousDecision`仅保留上次被接受的公开决定和计划时长，不保存私密推理。
- 交棒计时以实际播放完成回执起点为准，不从生成结束或稍迟的调度tick开始。自己的讲话时间不被算进留白；无转写的讲话仍会延后静默观察。
- 模型说明与手册统一：`programOpportunity=true`就是独立的自主判断机会，无需新主播/弹幕消息。持续主持下0表示不指定等待时长，安静30秒仍会复查；有限模式才仅等待新输入。到点允许选择接播或新的有时限留白，并非强制每次发声。
- 明确区分人工暂停与留白，时间不能恢复暂停/关闭的主持。新输入、停止、静音、断线和版本校验保留。时间字段不参与任务去重key，不会因为每秒变动而持续请求模型。
- 本机`live_context` MCP也返回相同的时钟与主持时间上下文；正常定时复查已附带这些信息，不需要先查工具。

没有修改ASR、Qwen发声、前端播放或接管阈值，也没有新增网页。手册说明继续由原生「直播助播」设置读取后端。

## 验证

- `npm run check`、523项Node测试通过。新增模拟时钟测试覆盖无人输入到点、时间刷新、重复等待不丢失真实安静时长、真实播放完成起点、人工暂停/停止/新输入撤销计时依据。
- 实际HTTP服务器测试经过约15.2秒真实墙钟：没有发送主播或观众消息，后台调度器自动第二次调用导演，带新的时间、预约唤醒原因和至少15秒留白；保持舞台心跳，最后人工暂停取消后续预约。该测试使用模型边界替身、无ASR/TTS，区别于真实模型测试。
- 真实DeepSeek、隔离合成对话与模拟经过时间，最终5/5：预约30秒到点接播、0的30秒静默唤醒接播、反复留白后接播、3秒未到点等待、人工暂停180秒仍等待。台词/理由/完整快照及源码哈希保存在`data/hosting-clock-trial-1792497350179/report.json`。
- 前两轮动作也为5/5，但暂停理由仍说“等安静够了再说”，与暂停边界不一致。增加显式暂停说明后，最终理由为“持续主持已被暂停，现场也没人接话，我不自己恢复播”。保留`data/hosting-clock-trial-1792497132506/report.json`、`data/hosting-clock-trial-1792497292244/report.json`，无自动重试或删失败样本。
- 初始播放测试夹具20秒不发进度回执触发了既有播放超时，改成每10秒正常进度；未放宽生产超时。HTTP夹具第一次以空模型密钥启动主持被503拒绝，改用假凭据和替身规划器，未更改生产鉴权。
- 上述不是本轮真人语音或长时间自然度验收。有限真实模型样本证明这些测试场景的行动选择；不保证每次留白之后都立即发声。

日志：`data/hosting-clock-check.log`、`data/hosting-clock-all-tests.log`、`data/hosting-clock-tests.log`、`data/hosting-clock-http.log`。复跑真实模型用[hosting-clock-trial.mjs](../scripts/hosting-clock-trial.mjs) `--real`与已有本机凭据。
